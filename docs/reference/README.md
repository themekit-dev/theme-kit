# Theme Kit — docs system reference

Canonical, machine-checkable artifacts for the documentation pipeline.

## What lives here

| Path                                | Kind       | Owner                                                            |
| ----------------------------------- | ---------- | ---------------------------------------------------------------- |
| `capabilities.ts`                   | authored   | capability ↔ package ↔ symbol registry (brief §4). Never edited by tooling. |
| `public-api.json`                   | generated  | `scripts/docs/public-api.mjs` — every shipped export, classified (§7). |
| `baselines/snippet-baseline.json`   | generated  | `scripts/docs/snapshot-snippet-baseline.mjs` — the frozen docs floor (Audit A). |
| `baselines/audit-g-terminology.allowlist.json` | generated | `scripts/docs/audits/audit-g-terminology.mjs --update` — Audit G allowlist. |

## Where the pages live (decision)

The brief's `docs/**` tree is mapped onto the **existing `apps/docs` site**;
this directory holds only generated/canonical *data*.

- Prose + code live in `apps/docs/{app,lib,content}` — the deployed site.
- The brief's `docs/reference/api/**` corresponds to the site's existing,
  already-gated `/api-reference/{package}` pages, generated by
  `apps/docs/scripts/generate-api-reference.mjs`.
- Rationale: brief §16 says to preserve the existing package map, exports maps
  and snippet audit; §14 forbids "the same non-trivial code appearing in two
  places without a canonical source". Building a second source tree would
  duplicate the site.

A `§3` page *contract* (the required section list) is therefore enforced against
the existing pages rather than against a new `docs/**` tree.

## Gates

| Command                                        | Enforces                                                                 |
| ---------------------------------------------- | ------------------------------------------------------------------------ |
| `node scripts/docs/public-api.mjs`             | §7: every shipped export is classified; fails on unclassified exports and on any disagreement with the frozen manifest. |
| `node scripts/docs/audits/audit-e-invented-symbols.mjs` | §8 Audit E + §4: registry entries must be shipped symbols; every doc import must be listed in `capabilities.ts`. |
| `node scripts/docs/audits/audit-f-internal-symbols.mjs` | §8 Audit F: no doc and no registry entry may reference an `INTERNAL` symbol. |
| `node scripts/docs/snapshot-snippet-baseline.mjs` | §8 Audit A floor: docs must not shrink and no baseline reference may vanish. |
| `node apps/docs/scripts/generate-api-reference.mjs --check` | §14: regenerates every API page **in memory** and compares — a hand-edited or stale file under `apps/docs/content/api-reference/**` fails. No `--check`, the generator writes. |
| `node scripts/docs/audits/audit-b-package-to-docs.mjs --coverage=fail` | §8 Audit B: every shipped public export lands on its generated API page and has a registry/guide destination. |
| `node scripts/docs/audits/audit-c-examples.mjs` | §8 Audit C (static): every `examples/**/example.meta.json` is internally consistent with the shipped surface, **and §13 coverage** — every capability slug in the registry has at least one example. |
| `node scripts/docs/audits/audit-c-examples.mjs --offline` | §8 Audit C (offline): compiles each example's sources against the workspace's **built `.d.ts`**, then bundles framework examples with esbuild and **renders them with `react-dom/server`** so the component tree actually executes. Deterministic, no `npm install`, no network. This is the `--full` gate step. |
| `node scripts/docs/audits/audit-c-examples.mjs --dynamic` | §8 Audit C (dynamic, strongest): packs each declared package, installs a temp consumer fixture from those tarballs, then typechecks and smoke-runs the example. Needs `pnpm` + network (~4 min for 21 examples); uses a private npm cache per run. |
| `node scripts/release/audit-dependencies.mjs`  | §8 Audit D: dependency isolation — no forbidden edges, every peer earned. |
| `node scripts/docs/audits/audit-g-terminology.mjs` | §8 Audit G: canonical vocabulary across JSDoc, guides, README, examples, CLI docs. Allowlist: `baselines/audit-g-terminology.allowlist.json`. |
| `node scripts/docs/audits/audit-page-contracts.mjs` | §2 IA integrity + all three §3 page contracts: **feature (§3.1)** — every `core-feature` capability's guide links its generated API reference; **framework (§3.2)** and **adapter (§3.3)** page shape, plus a sidebar entry for every framework/adapter entry; **tooling (§3.4)** — the CLI section covers Installation / Overview / Commands / Configuration / CI & Automation / a complete example, and every tooling page links its generated API reference. Also flags `content/*.md` that no route renders. |
| `node scripts/docs/audits/audit-browser-smoke.mjs` | §8 Audit H: docs build + browser smoke against the built site. |
| `node scripts/docs/release-gate.mjs` | §9: runs every gate above (except the baseline update) sequentially; any failure blocks release. |
| `node scripts/docs/release-gate.mjs --full` | §9 + API-reference drift check, offline example verify, `next build` and Audit H `--strict`. |
| `node scripts/docs/release-gate.mjs --full --dynamic` | §9 end to end, adding the dynamic consumer-compile (`docs:release-gate:all`). |

`pnpm` is broken in this environment (`corepack` shim); run the scripts directly
with `node`, or `npx --yes pnpm@10 <script>`.

Run them **sequentially**: the audits spawn `scripts/release/snippet-audit.mjs`
and share a temp report file.

> **Windows lock caveat.** `apps/docs/.next` can intermittently end up locked, in
> which case `next build` prints the full route table and exits 0 but leaves a
> **partial** artifact (no `BUILD_ID`, no `app-path-routes-manifest.json`). The
> gate asserts those files exist after the build and fails with a clear message
> instead of letting Audit H report hundreds of bogus failures. To clear a locked
> tree, delete `.next` with Node rather than `rm` (msys `rm -rf` hangs on a locked
> tree; `fs.rmSync` succeeds immediately):
> `node -e "require('fs').rmSync('apps/docs/.next',{recursive:true,force:true})"`.

## Workflow when the public surface changes

1. Rebuild the package (tsup + tsc).
2. `node scripts/release/export-inventory.mjs` — regenerates
   `scripts/release/api-manifest.json` (the exports authority).
3. `node scripts/docs/public-api.mjs` — regenerates `public-api.json`.
4. `node scripts/docs/audits/audit-e-invented-symbols.mjs` and
   `.../audit-f-internal-symbols.mjs`.
5. `node scripts/docs/snapshot-snippet-baseline.mjs` — if a reference change was
   deliberate, re-freeze with `--update` (the gate prints exactly what changed).

The registry records the shipped truth only. If a symbol is not exported, it is
not listed — even if a page wants it. Fix the page or promote the symbol
deliberately; never widen the registry to silence a failure.

## Findings recorded by these gates (2026-09-15)

1. **Fixed — docs bug.** `apps/docs/lib/use-cases.ts` imported
   `ThemeTransitionOptions` from `@theme-kit/next/client`, which does not export
   it (it ships from `@theme-kit/core`). The existing snippet audit could not
   catch this: for subpath imports it verifies that the *subpath* exists, but
   never that the *symbol* exists inside it. Audit E now covers that gap.
2. **Resolved — Nuxt parity gap.** `packages/nuxt/src/runtime/composables/index.ts`
   defined `useThemeMode`, `useThemeFamily`, `useThemeValue`, `useThemeTokens`
   and the module auto-imported them, but the `@theme-kit/nuxt` root re-exported
   only 9 of Vue's 13 composables, so `import { useThemeMode } from
   "@theme-kit/nuxt"` failed while `useThemeMode()` worked under Nuxt
   auto-imports. Decision (additive, non-breaking): **promote the four
   re-exports** — the root already re-exported the rarer siblings
   (`useThemeBatch`/`useThemeSnapshot`/`useThemeRestore`/`useThemeLifecycle`/
   `useThemePacks`/`useThemeSchedule`), so the omission was inconsistent rather
   than deliberate, and all four are already part of the module's own public
   surface. Vue-internal plumbing with no Nuxt meaning (`ThemeKitSymbol`,
   `ThemeScheduleController`, `createVueThemeBootstrapScript`,
   `provideThemeRuntime`) stays intentionally unre-exported. Shipped as a minor
   changeset; `public-api.json` went 913 → 917 symbols.
3. **Brief vs repo.** Audit A's stated baseline ("158 imports / 66 pages") is
   stale: the actual floor is 134 pages / 438 references. §2's IA omits
   `@theme-kit/tailwind` and `@theme-kit/unocss` (both shipped and documented)
   and lists Mantine under Adapters, which `update.md` records as deliberately
   wrong (Mantine ships a provider-based bridge, not a `ThemeAdapter`). The
   brief says "Theme Kit 1.0"; packages are at 1.3.0.

## §12 / §13 status

**Nothing from §12 remains unwired**, and **§13's coverage criterion is met and
enforced**: `audit-c-examples.mjs` reports
`§13 coverage: 20/20 capabilities have an example` and fails if any capability
slug has no example (negative-tested). 21 examples exist in total — the 20
capabilities plus `basic-theme`, a getting-started example that is not itself a
capability.

All three §3 page contracts are now enforced (§3.1 feature, §3.2 framework,
§3.3 adapter, §3.4 tooling) by `audit-page-contracts.mjs`.

`--full` is the only tier that needs external tooling (Chromium + `ws`); the
static and offline-typecheck tiers run anywhere.

Adding a new capability to the registry therefore also requires adding an
example, or the gate fails — which is the point.

## Done since this README was written

- **§6.4 capability backlinks.** Every capability in `capabilities.ts` now
  declares a `guide` route (the owning page on the docs site, per
  `apps/docs/lib/docs-routes.ts`), and `generate-api-reference.mjs` appends a
  generated "Related docs" section linking each API page back to the
  capabilities that list its package/entrypoint. All 54 pages regenerated.
- **Audit B wired** (`docs:audit:b`) — every shipped public export has an API
  page; registry coverage reported (hard-gates with `--coverage=fail`, which
  currently passes: 0 uncovered of 869).
- **§9 release gate wired** (`docs:release-gate` →
  `scripts/docs/release-gate.mjs`): runs public-api --check, export-inventory,
  the snippet-baseline floor, Audit B (--coverage=fail), Audit C (static),
  Audit E and Audit F sequentially; any failure blocks release.
- **Audit D folded in** (`docs:audit:d`) — `scripts/release/audit-dependencies.mjs`
  is now a gate step (0 violations).
- **Audit G wired** (`docs:audit:g`) — canonical-vocabulary audit across 674
  prose files. Two real bugs fixed while wiring it: the audit's own JSDoc header
  contained `*/` sequences that terminated the comment early (a syntax error),
  and its allowlist path pointed at a non-existent `scripts/docs/baselines/`.
  Fixed one root-cause prose violation (`packages/core/src/presets.ts` said
  "preset theme variant"; the canonical word is "mode").
- **§3 page contracts + §2 IA wired** (`docs:page-contracts`) — every
  `DOCS_ROUTES` href resolves to a concrete app route, every capability `guide`
  is a real route, and every framework/adapter entry satisfies its §3 content
  contract.
- **Audit H wired** (`docs:audit:h`) — docs build + browser smoke over every
  route (HTTP 200, no console errors, non-empty hydration, generated API pages
  expose their package + "Related docs", framework pages use "mode" not
  "variant"). `--full` runs the build + Audit H with `--strict`.
- **Audit H `--strict` was a no-op (fixed).** `skip()` set
  `process.exitCode = 1` and then called `process.exit(0)`, which overrides it —
  so `--strict` (and therefore the `--full` gate) silently *passed* when the
  browser toolchain was missing, exactly the "shipping drift" the brief forbids.
  It now calls `process.exit(1)`. Negative-tested both ways.
- **`--full` asserts the build artifact.** `next build` can exit 0 with an
  incomplete `.next`; the gate now checks `BUILD_ID`,
  `app-path-routes-manifest.json` and `prerender-manifest.json` after the build
  and fails loudly, rather than letting Audit H report misleading failures.
- **Audit C's dynamic half works** (`docs:audit:c:dynamic`). Two real bugs had to
  be fixed in `scripts/docs/lib/consumer-compile.mjs` before it would run:
  1. `execSync` was called but never imported — the harness crashed outright.
  2. The fixture wrote **relative** `file:../tarballs/x.tgz` specifiers. When a
     packed package itself depends on another packed package
     (`@theme-kit/react` → `@theme-kit/core`), npm re-resolves that relative
     path from a different base and **hangs forever** in `idealTree buildDeps`
     instead of failing. Now absolute, which installs in ~6s.
  It also resolved npm via a `shell: true` PATH lookup, which on Windows can
  pick a different (corepack/shim) npm; it now invokes the npm CLI through the
  node that is running the audit, and bounds the install with a timeout so a
  deadlock fails the gate instead of hanging it.
- **The offline tier now *renders* framework examples, not just compiles them.**
  `--offline` (renamed from `--typecheck`, since it does more than typecheck)
  bundles each React example with esbuild and renders it via `react-dom/server`,
  so the component tree executes. Typechecking cannot catch runtime-only
  failures: a deliberately injected `useTheme()` outside its provider typechecks
  cleanly and fails at render with
  `Error: useThemeRuntime must be used inside ThemeProvider` — which the smoke
  now catches (negative-tested, exit 1). All 10 React examples render (122–2068
  chars); the 11 framework-free examples are executed by the dynamic tier's smoke
  step instead.
- **Temp-directory collisions fixed.** Both tiers named their scratch directory
  from `basename(exampleDir)` — which is literally `react` for *every* React
  example, so all of them shared one path and a crash in one could leave state the
  next silently reused. Now derived from the path
  (`examples-theme-scope-react`). Two error paths in the new render smoke also
  leaked their temp dir; both are now behind a `finally`.
- **The dynamic tier's stall is fixed — it was the machine's npm cache.** The
  `--dynamic` install had been stalling indefinitely at
  `fetch manifest …@file:<tarball>`. Isolated with a controlled experiment:
  **3/3 installs timed out on the shared (default) npm cache, 3/3 succeeded in
  ~3.5s each with a per-run cache directory.** npm locks its cache, and a cache
  left in a bad state by an interrupted install makes later installs block
  instead of fail. The harness now passes `--cache=<per-run dir>`
  (`THEME_KIT_AUDIT_C_CACHE` overrides). Result: `--dynamic` passes for all 21
  examples in ~4 min, and is now a gate tier (`--full --dynamic`, i.e.
  `docs:release-gate:all`) rather than an unreachable pre-release step.
- **Canonical examples: 2 → 21, covering 20/20 capabilities.** Every capability in
  the registry now has an example, and `audit-c-examples.mjs` fails if one is
  missing. React examples (`theme-scope`, `families-modes`, `transitions`,
  `scheduling`, `custom-scrollbar`, `history`, `snapshots`, `persistence`,
  `devtools`) use `@theme-kit/react`; framework-free ones (`themes`, `tokens`,
  `runtime`, `scopes`, `multi-window-sync`, `sunrise-sunset`, `accessibility`,
  `theme-generation`, `plugins`, `zero-flash`, `cli`) use `@theme-kit/core` or
  `@theme-kit/cli` and are single-file, so they are **executed** by the dynamic
  tier's smoke step.
- **A real defect found in the pre-existing `basic-theme` example.** It called
  `defineTheme({ name, light, dark })`. That is **not** the theme shape —
  `ThemeDefinition` is `{ name, extends?, meta?, tokens? }`, one definition per
  mode, grouped by `meta.family` / `meta.mode`. It typechecked only because
  TypeScript skips excess-property checks when the contextual type is a bare
  type parameter, so the example silently produced a theme with **no tokens**.
  Fixed across every example, and the docs' canonical shape
  (`meta: { family, mode }` + `tokens`) is now what the examples use.
- **§3.4 tooling page contract enforced, and it caught a real gap.** The
  page-contract audit previously covered only framework (§3.2) and adapter (§3.3)
  pages; §3.4 (tooling) was unenforced. It now checks that the CLI section covers
  Installation / Overview / Commands / Configuration / CI & Automation / a
  complete example (all satisfied by `content/cli/*.md`), and that **every
  tooling page links its generated API reference instead of duplicating it**.
  That last rule immediately failed on `app/devtools/page.tsx`, which had no
  link to `/api-reference/devtools` — a genuine §3.4 gap, now fixed by adding the
  section (and its TOC heading).
- **Unreachable prose is now detected — and it found 2,038 lines of it.**
  A `content/*.md` that no `getContent("<slug>")` call reads is invisible on the
  site, and nothing noticed: the file exists (so it isn't "missing"), it isn't a
  route (so no link check touches it), and Audit A counts its snippets without
  caring whether anyone reads them. The audit now requires every `content/*.md` to
  be rendered by a route.

  Five files failed. I then **measured** how much of each one the live source
  already carries (snippets present verbatim + prose-vocabulary overlap) rather
  than judging by heading structure — which turned out to matter, because the
  headings are misleading:

  | File | Lines | Snippets carried | Prose | Disposition |
  | ---- | ----- | ---------------- | ----- | ----------- |
  | `devtools.md` | 137 | 5/5 | 100% | fully superseded — safe to delete |
  | `architecture.md` | 247 | 13/13 | 87% | fully superseded — safe to delete |
  | `framework-guides.md` | 723 | **8/36** | 86% | *not* superseded — 28 snippets exist only here |
  | `animation.md` | 247 | **2/13** | 60% | *not* superseded — 11 snippets exist only here |
  | `adapters.md` | 684 | **7/33** | 36% | *not* superseded — 26 snippets exist only here |

  I initially called three of these "safe to delete" on heading structure alone;
  `framework-guides.md` has the same section list as the live pages but only 22%
  of its snippets carry over. ~616 lines of snippet text have no counterpart
  anywhere else, so only **two** are genuinely superseded. All five are
  **recorded, not deleted** — that is a maintainer call, not an inference of mine
  to act on. The audit prints each with its measured evidence and passes; adding a
  *new* unrendered file fails (negative-tested).
- **Every framework and adapter page must now be reachable from the sidebar.**
  The §2 checks only ran the other way round — every sidebar href must resolve,
  and every *capability* guide must be listed. So an entry added to
  `frameworks.tsx` or `libraries.tsx` could ship a working page with no sidebar
  link and nothing would fail; the existing check only caught it if
  `capabilities.ts` happened to point at the same route. The audit now also walks
  the `slug` of every framework/adapter entry and requires
  `/framework-guides/<slug>` / `/libraries/<slug>` in `docs-routes.ts`.
  Negative-tested both ways (removing the React and the daisyUI sidebar entries →
  exit 1, then restored).
- **§3.1 feature-page contract enforced — the last unenforced §3 contract.**
  §3.2 (framework), §3.3 (adapter) and §3.4 (tooling) were checked; §3.1
  (feature pages) was not. Its enforceable core is its last bullet plus §14's
  *"feature pages duplicating the API reference instead of linking it"*, so every
  `core-feature` capability's guide must now link a generated API reference.

  Scope comes from the registry, not guesswork: `category` separates §2's
  **Concepts** (themes, tokens, families/modes, runtime, scopes) from its
  **Features** and **Tooling**, so `/architecture` and `/core-concepts` are not
  feature pages and correctly need no API-reference section. The check follows
  markdown-driven guides (`app/advanced-features/page.tsx` renders
  `content/advanced-features.md`) and thin wrappers
  (`app/animation/page.tsx` → `AnimationGuide.tsx`).

  It found **six** feature pages with no API-reference link, now fixed:
  `/persistence`, `/plugins`, `/zero-flash` (plain sections) ·
  `/accessibility`, `/multi-window-sync` (sections, auto-collected TOC) ·
  `/advanced-features` (markdown) · `/theme-studio` (bare tool page) ·
  `/animation` (had a `#api-reference` section that restated the exports in a
  table — the §14 anti-pattern exactly — so it now also links the generated one).
- **"Don't hand-edit generated files" is now enforced.** `CONTRIBUTING.md` listed
  *"Hand-editing anything under `apps/docs/content/api-reference/**`"* as an
  anti-pattern **blocked by CI** — but the generator had no `--check` mode and
  only ever wrote, so nothing enforced it. It now regenerates every API page in
  memory and compares (`generate-api-reference.mjs --check`, `docs:api:check`),
  reporting drifted / missing / unexpected files. Negative-tested: a one-character
  edit to `core.md` → `1 drifted`, exit 1. Runs as the first `--full` gate step
  (~2 min, 54 files). A `--packages=` scope skips the "unexpected" sweep, since a
  scoped run deliberately owns only a subset.
- **`CONTRIBUTING.md`** now documents the §10 change workflow (API → JSDoc →
  build → exports → registry → guide → regenerate → gates), including the
  "never start by editing the visible docs page" rule.
