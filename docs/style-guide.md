# Documentation style guide

**Status: internal maintainer artifact. There is no public `/docs/style-guide`
route, and there should not be one.** A public page describing how Theme Kit's
documentation is written does not help anyone use Theme Kit; it would compete
with product documentation in the public IA. The public site simply benefits
from the standard being applied.

This guide is normative for anything under `apps/docs/` — pages, content
markdown, components, and generated files.

---

## 0. The one rule

**The shipped package is the only source of truth.** If the docs and the code
disagree, the code wins and the docs are the bug. Everything below exists to make
that disagreement impossible rather than merely unlikely.

---

## 1. Never hand-write what can be generated

If a fact already exists in the repository, read it at build time. A
hand-maintained copy is a bug with a delay fuse.

| Fact | Generated by | Gate |
| --- | --- | --- |
| API surface per package | `scripts/generate-api-reference.mjs` (TypeDoc → `content/api-reference/**`) | `api:check` |
| CLI commands, options, exit codes | `scripts/generate-cli-reference.mjs` (from `packages/cli/src/cli.ts`) | `cli:check` |
| Package dependencies / used-by / peers / subpaths | `scripts/generate-package-graph.mjs` → `lib/generated/package-graph.ts` | `packages:check` |
| Example catalogue | `scripts/generate-examples.mjs` (from `examples/**/example.meta.json`) | `examples:check` |
| Documented API names | `scripts/verify-package-apis.mjs` (against built exports) | `apis:check` |
| Internal links, duplicate titles, sitemap coverage | `scripts/check-links.mjs` | `links` |

Generated regions are fenced with explicit markers and a "do not edit by hand"
note naming the command to run:

```md
<!-- cli-command:generated:start -->
> Generated from `packages/cli/src/cli.ts` … run `pnpm --filter @theme-kit/docs cli:generate`.
<!-- cli-command:generated:end -->
```

Surrounding hand-written prose is preserved; only the drift-prone region is
replaced. When you remove a hand-written table in favour of a generated one,
**carry forward any prose that was not part of the table** rather than deleting
it with the table.

### The split: structure generated, judgement authored

Some things a manifest cannot express — why a package exists, how hard an example
is, what a reader takes away. Put those in an **editorial layer** keyed by the
generated identifier (`lib/package-map.ts`, `lib/examples.ts`), never inline in
the page:

- A new package or example still renders if it has no editorial entry (falling
  back to its own description) and is listed as incomplete, so it surfaces as a
  gap instead of vanishing.
- Editorial layers may only add judgement. If you find yourself restating a
  dependency, a version, or a file path, it belongs in the generator.

---

## 2. Verify claims against the artefact, never against memory

Authoring an API name, a default value, or a count from inference is how a
reference page becomes confidently wrong. `/package-map` documented eight
invented export names on its first draft; the verifier caught all eight.

Before a claim ships:

- **API names** → `apis:check` (runtime exports, falling back to `.d.ts` for
  type-only exports and for `solid`/`angular`, which cannot be imported outside
  their own environment).
- **Counts** ("34 themes", "nine families", "11 framework guides") → run the
  function and read the number.
- **Variable names** → run the emitter. Token keys are emitted **verbatim**:
  `colors.primaryForeground` produces `--theme-color-primaryForeground`. The
  kebab form (`--color-primary-foreground`) exists only as a Tailwind-side alias
  and resolves to nothing on its own.
- **Symbols** → Audits E and F. A symbol referenced in the docs must exist in the
  shipped surface **and** be listed in `docs/reference/capabilities.ts` — and must
  not be classified `INTERNAL`. Documenting an `/** @internal */` export is a
  defect even though it type-checks.

## 3. Page structure

Every page renders inside `DocsLayout` and opens with `PageHeader`.

```tsx
<DocsLayout>
  <div className="max-w-3xl">        {/* or max-w-4xl for reference tables */}
    <PageHeader
      eyebrow="Reference"             {/* the sidebar section it belongs to */}
      title="Package map"
      description="One or two sentences: what this page answers."
      verified={{ version: PKG_VERSION, date: "September 18, 2026" }}
    />
    …sections…
    <RelatedLinks links={[…]} />
  </div>
</DocsLayout>
```

Rules:

1. **Exactly one `<h1>` per page.** It comes from `PageHeader`, never from
   markdown. Content markdown that renders under a page starts at `##`.
2. Sections use `SectionHeading` with a stable `id` (it becomes the "On this
   page" anchor).
3. Number sections only when the page is a sequence (`num={1}`, `num={2}` …).
4. End with `RelatedLinks` — three to six destinations, each with a one-line
   reason to go there.
5. `verified` is required on reference pages that make version-specific claims.
6. Reach for a shared component before a new one. The inventory is
   `components/ui/`: `PageHeader`, `SectionHeading`, `Callout`, `CodeBlock`,
   `RelatedLinks`, `Badge`, `ApiSymbol`, `CommandReference`, `FeatureGrid`,
   `PickCard`, `Prerequisites`, `NextStepCard`, `SupportBadge`, `VersionBadge`,
   `DocHeader`, `CopyButton`.

### Heading hierarchy

Never skip a level (`##` → `####`). Do not use `#` for emphasis, and never inside
a code fence expecting it to be a heading — a `#` line in a ```bash block is a
shell comment. Audit your headings with a scanner that skips fenced blocks; a
naive `grep '^#'` reports shell comments as `<h1>`s.

## 4. Terminology

Canonical vocabulary is enforced by **Audit G** across JSDoc, guides, READMEs,
examples and CLI docs. Use these forms:

| Use | Not |
| --- | --- |
| theme family | theme set, palette group |
| mode (`light` / `dark`) | theme mode, colour scheme |
| selection (`{ family, mode }`) | theme state, current theme object |
| theme runtime | manager, controller, engine instance |
| semantic token | design token, variable (when you mean a token) |
| theme definition | theme config, theme object |
| scoped theme | nested theme, local theme |
| pre-paint bootstrap | blocking script (in prose — fine in code identifiers) |
| zero flash | no flicker, FOUC-free |
| framework integration | adapter (reserve "adapter" for UI-library adapters) |

Additional rules:

- **Package names are exact and scoped**: `@theme-kit/next`, never "the Next
  package" on first mention.
- **Framework names**: React, Next.js, Vue, Nuxt, Svelte, SolidJS, Angular,
  Astro, Remix, Tailwind CSS v4.
- Prefer "reach for it when…" over "you should…".
- Do not invent a capability name. If it is not in
  `docs/reference/capabilities.ts`, it does not exist.

## 5. Code examples

**Examples must be real.** A snippet invented alongside the prose drifts
immediately and cannot be verified.

- Prefer reading the file at build time over transcribing it. `/examples` shows
  each example's actual entry file, read from `examples/` — the page cannot
  describe an implementation that does not exist.
- Every snippet must be runnable as written: correct imports, no elided setup
  that changes behaviour.
- **Emit the CLI's own output verbatim** rather than re-rendering it. Re-rendering
  the `--help` block collapsed its column alignment and folded the title into the
  summary; the fix was to print the source string unchanged.
- Keep one idea per snippet. If it needs two, split it.
- Show the *why* in a comment only when the code alone does not reveal it.
- Highlighting happens server-side via `highlightCode(code, lang)`; render with
  `CodeBlock` (`html`, `code`, `language`, optional `filename`). Pass a
  `filename` whenever the snippet is a real file — it lets a reader find it.
- Mark optional or illustrative lines explicitly rather than silently omitting
  them.
- Never reference an `INTERNAL` symbol (Audit F).

### Framework-specific notation

- Label the framework on every framework-specific snippet (`// app/layout.tsx`
  or the `filename` prop) — readers arrive mid-page from search.
- Where a pattern differs per framework, show the canonical one and link the
  framework guide instead of reproducing four variants.
- Framework limitations belong in `lib/framework-caveats.ts` so every guide states
  them identically.

## 6. Callouts and admonitions

Use `Callout` with the narrowest fitting variant: `info`, `tip`, `warning`,
`important`, `limitation`, `success`, `neutral`.

- **`limitation`** is for honest boundaries. Theme Kit documents what it does not
  do; do not soften a real limitation into a `tip`.
- One callout per idea. Two stacked callouts means the prose needs rewriting.
- Give it a `title` unless the variant icon alone is unambiguous.
- A `warning` must describe a consequence, not just caution: "A concrete mode
  must not use media queries — both blocks target `:root`, so a `light` selection
  would still follow an OS-dark visitor."

---

## 7. Tabs

Interactive tabs use the WAI-ARIA tablist pattern — this is not optional
decoration. `aria-selected` on a plain `<button>` is **invalid and ignored**;
screen readers then announce identical buttons and never say which is active.

```tsx
<div role="tablist" aria-label="Package manager">
  <button role="tab" id={tabId(m)} aria-selected={active === m}
          aria-controls={panelId} tabIndex={active === m ? 0 : -1}
          onKeyDown={onKeyDown}>{m}</button>
</div>
<div id={panelId} role="tabpanel" aria-labelledby={tabId(active)}>…</div>
```

Requirements: `role="tablist"` with an `aria-label`, `role="tab"` with
`aria-selected` / `aria-controls` / `id`, a `role="tabpanel"` linked back by
`aria-labelledby`, roving `tabIndex`, and Arrow / Home / End key handling. Use
`useId()` for ids so multiple instances on a page do not collide.

## 8. Accessibility requirements

Every page must pass, at 320 px and 375 px as well as desktop:

- One `<h1>`; no skipped heading levels.
- Every interactive element has an accessible name (visible text, `aria-label`,
  `aria-labelledby`, or an explicit/wrapping `<label>`). A `placeholder` is **not**
  a name.
- Images have `alt` (empty `alt` for decorative).
- The active navigation item carries `aria-current="page"` — never conveyed by
  colour alone.
- Navigation regions are `<nav>` landmarks with `aria-label`; the docs sidebar is
  `<nav aria-label="Documentation">`.
- Modal surfaces are hidden from assistive tech when closed (`inert` +
  `aria-hidden`) and are `role="dialog"` with `aria-modal` and a label.
- No page-level horizontal overflow. Wide content (tables, code) scrolls inside
  its own container, never by pushing the page.
- Respect `prefers-reduced-motion` for actual motion (transforms, parallax,
  reveals). Colour-only transitions are not motion and need no guard.

Note the two-dialog trap when writing probes: the docs drawer and the search
palette are both `role="dialog"`. Target them by `aria-label`, not by document
order.

## 9. SEO and frontmatter

- **Every route declares its own canonical** via `alternates: { canonical:
  docsUrl("/route") }`. Never declare `alternates.canonical` in a layout: Next
  merges layout metadata into every page, so one line there makes all ~66 routes
  claim the homepage as their canonical.
- `title` is unique across the site; `check-links.mjs` fails on duplicates. The
  layout appends `— Theme Kit`.
- `description` is one sentence, 120–160 characters, describing the page's
  answer rather than repeating its title.
- Add the route to `lib/docs-routes.ts`. That single entry feeds the sidebar,
  prev/next pagination, the search index and the sitemap.
- Open Graph images come from the shared renderer `components/og/card.tsx`.
  Do not invent a "live demo" URL for something that is not deployed — a
  fabricated link is worse than none.

---

## 10. Related-docs conventions

- Use `RelatedLinks`, three to six entries, each with a one-line reason.
- Link to the **narrowest** page that answers the reader's next question.
- Never link a page to itself, and never duplicate a link already in the
  surrounding prose.
- Migration and deprecation language: name the version and the replacement, and
  state whether the old form still works. "Deprecated in 1.3.0, still accepted;
  removed in 2.0" — never "will be removed in a future release".

## 11. Example quality requirements

Every example under `examples/` carries an `example.meta.json`; Audit C validates
it against the shipped surface and §13 capability coverage.

```json
{
  "feature": "persistence",
  "framework": "react",
  "packages": ["@theme-kit/core", "@theme-kit/react"],
  "peerDependencies": ["react", "react-dom"],
  "files": ["src/App.tsx"],
  "entry": "src/App.tsx",
  "prerequisites": [],
  "expectedExportsUsed": ["defineTheme", "createDefaultPersistence", "ThemeProvider", "useTheme"]
}
```

Requirements:

- `expectedExportsUsed` must list only shipped public exports (Audit C and
  `apis:check` both enforce this).
- `entry` names the file a reader should open first, and it must be in `files`.
- `prerequisites` is empty when the example is self-contained — do not pad it.
- One example demonstrates one feature. A second feature belongs in its own
  example or the recipe pages.
- Examples are the canonical implementation of a documented snippet, not a
  variant of it. If a framework guide's setup changes, the example changes with
  it.

## 12. Before you open a PR

Run the gates **sequentially** — they share a temp report file.

```bash
node apps/docs/scripts/check-links.mjs
node apps/docs/scripts/generate-package-graph.mjs --check
node apps/docs/scripts/generate-examples.mjs --check
node apps/docs/scripts/generate-cli-reference.mjs --check
node apps/docs/scripts/generate-api-reference.mjs --check
node apps/docs/scripts/verify-package-apis.mjs
node apps/docs/../…/typescript/bin/tsc --noEmit        # inside apps/docs
```

Then the repository audits that this guide is accountable to:

```bash
node scripts/docs/audits/audit-e-invented-symbols.mjs
node scripts/docs/audits/audit-f-internal-symbols.mjs
node scripts/docs/audits/audit-g-terminology.mjs
node scripts/docs/audits/audit-i-generated-tables.mjs
node scripts/docs/audits/audit-c-examples.mjs
node scripts/docs/audits/audit-page-contracts.mjs
```

`tsc` alone is not evidence that a snippet is correct: no typechecker sees code
inside a template literal or a fenced block. And a green import audit is not an
accuracy audit — it proves the import resolves, not that the call is right.
